# Правила проекта 1С

## Что это за репозиторий
- `src/` — конфигурация, выгруженная из Конфигуратора в файлы (XML + модули .bsl, иерархический формат).
- `tools/` — скрипты среды: `setup.sh`, `bsl-check.sh`, `rlm.py`.
- Изменения из `main` загружаются в базу на рабочем сервере скриптом `tools/load-to-base.bat`.

## Начало каждой сессии
1. `bash tools/setup.sh` — если инструменты ещё не установлены.
2. Работать в отдельной ветке `feature/<кратко-о-задаче>`, не прямо в `main`.

## Как искать в коде (экономия контекста)
- Не читать модули целиком. Сначала структура, потом нужная процедура:
  `~/.local/share/uv/tools/rlm-tools-bsl/bin/python tools/rlm.py src "<вопрос>" "<python с хелперами>" "<домены>"`
  Примеры хелперов: `find_module("Имя")`, `extract_procedures(path)`, `get_object_profile("Имя")`.
- Для простых поисков достаточно `grep -rn` по `src/`.

## Правила доработок
- Писать по стандартам 1С (its.1c.ru/db/v8std): русские идентификаторы, комментарии к экспортным методам, без запросов в цикле.
- Типовые объекты по возможности не менять — доработки через расширение или общие модули с префиксом компании.
- Изменённые места помечать комментарием `// <Компания> <дата> <задача>` ... `// Конец <Компания>`.
- Новые объекты метаданных (XML) — только если без этого нельзя; сообщать пользователю, что их нужно проверить в Конфигураторе.

## Кодировка и формат файлов — важно
- Модули `.bsl` и XML из Конфигуратора — UTF-8 **с BOM**, переводы строк как в исходном файле. Сохранять так же; не перекодировать.
- Не переформатировать файлы целиком: diff должен содержать только смысловые изменения.
- Файл `ConfigDumpInfo.xml` не редактировать вручную.

## Перед коммитом
1. `bash tools/bsl-check.sh --changed .` — ошибок уровня Error быть не должно.
2. Коммит с понятным описанием задачи, push в ветку, сообщить пользователю что изменено и какие объекты затронуты.
